# 04 · 实施路线与自动化调度

## 1. 先做什么

用户已确认第一阶段可用鼠标模拟输入。先做可复用的单人瞄准/开火/装填与回放，暂不接实体枪、Raw Input 或 Android 光枪插件。双平台开发保留；Android 第一阶段输入可使用外接鼠标与测试桥，触摸按需要增加。

第一目标不是一次生成六章成品，而是证明：**给定资源清单与机制规格，不用人工摆场景，可以生成、运行、检查、修复并交付一个短关卡**。

第二目标才是更换描述后仍能成功。只有一个固定样例通关，可能只是把一款游戏写死，没有证明工作流能重复使用。

## 2. 工具与工程结构

推荐工具：锁定版本的 Godot 标准版 + GDScript、匹配导出模板、Python 标准库调度器、Git、Android SDK/JDK/ADB、带 GPU 的渲染与烘焙节点。Godot CLI 用于导入、脚本执行和构建；调试预览在 Godot 编辑器完成。

MCP 是可选控制入口，用来查询节点、捕获状态或调用既有操作；主要链路必须能从 CLI/脚本复现，不让关键步骤只能靠 AI 点编辑器菜单。第一阶段不要求购买或安装 Blender MCP、3D 生成服务。

建议目录（下列为待实施结构）：

```text
game/
  project.godot
  core/                  输入/射击/伤害/导演/存档
  capabilities/          可组合与扩展机制
  assets/                原始资源与标准包装场景
  generated/             编译器输出，可重新生成
  overrides/             按 ID 定义的局部覆写
  tests/                 小场景与回放测试
  export_presets.cfg
pipeline/
  contracts/             版本化数据格式
  compiler/              规划/布局/场景编译
  validators/            规则与几何检查
  runners/               Godot/渲染/设备执行器
  prompts/               角色任务与产物要求
runs/<run_id>/           任务状态、日志、证据、成本
builds/<build_id>/       可交付文件与哈希
```

目前仓库新增的是 `docs/ai-workflow` 方案与数据预检样例，不是以上底座已实现。

## 3. 最小里程碑

### M0：环境、契约和资源包装

任务：检测 Godot/模板/Android 工具；锁版本；选最小已准备资源子集；完成导入、缩略图、尺寸与碰撞检查；定义 GameSpec、AssetManifest、LevelIR、事件、证据格式。

交付：资源目录和环境报告；一个能导入的标准敌人、建筑模块、交互物、反馈包；可执行静态预检。

退出：引用的资源能导入并实例化；格式错误、重复 ID 和缺资源能报告；同输入两次产生同规范化 IR 哈希。

本次附带样例完成的是契约预检演示，正式 Godot 导入与资源包装尚未完成。

### M1：固定镜头射击实验室

任务：InputHub、鼠标适配、ShotResolver、武器、部位伤害、敌人前摇/打断、反馈、HUD、暂停与测试桥。

交付：固定镜头小场景、回放输入、日志、Windows 与 Android 首次构建。Android 构建应从这一阶段开始，防止到最后才发现导出/资源不兼容。

退出：瞄准边界、空仓、装填、打断、暂停全部通过；从导出包可玩；输入到判定延迟有测量，帧间/物理 tick 语义明确。

### M2：程序化三驻点切片

任务：模块连接、镜头路径、Marker 锚点、事件调度、两型敌人、装饰禁布区、局部生成与预览。

交付：以约 90 秒为参考机器人目标的入口→走廊→中庭关卡；清场时长随玩家表现变化。AI 从规格生成 IR，编译器自动落场景。

退出：无人手摆场景即可重复构建；所有驻点无软锁；危险窗口可见性通过；修改装饰不会改变敌人编排。

### M3：分支、BOSS 与失败闭环

任务：救援成功/失败分支、汇合、弱点 BOSS、checkpoint、带误差机器人、截图/录像与修复归因。

交付：可重试的短完整游戏；机器可读报告；对典型错误能给出最小修改并重测。

退出：所有路径到终点；故意注入“弱点被墙挡”“最后敌人逃跑闸门不释放”“重复救援奖励”等问题均能检测，修复后稳定回归；PC/Android 包验证状态明确。

### M4：机制改描述后的复用验证

同一资源包执行三组要求：A 装填与精度；B 掩体＋限时评价；C 缴械＋救援选路。掩体键视为可映射输入。再引入一个库外但范围明确的新机制，例如击落飞行物触发场景机关。

交付：三个版本与一个新能力；需求→模块→场景→测试可追踪。

退出：所有版本不需人工逐关编辑，旧能力回归不被破坏，新能力必须通过独立与组合用例。记录成功率、重试次数、耗时和人工介入原因，不能凭一次成功宣称全自动。

### M5：批量生产与平台质量

任务：候选筛选、固定种子回归集、移动端预算、按驻点流送、画质预设、存档兼容与资源更新缓存。

交付：批量生成章节、版本比较、失败恢复、双平台构建及实机报告。

退出：在固定输入矩阵内完成可复现批处理；不同种子保持关键玩法约束；目标设备持续性能达标。真实双枪等进入独立后续里程碑。

## 4. 工期与成本的表达方式

这里不提供未经执行验证的“几天自动开发完成”承诺。先测 M0–M2 的导入时间、编译时间、AI 调用、候选失败率、试玩与实机排队，再估 M3–M5。

关键路径是：标准资源 → 射击底座 → 遭遇/镜头编译 → 自动试玩/证据 → 可复用机制验证。美术资源已充分准备，可以显著减少制作成本，但不会消除动画绑定、碰撞与游戏语义接入成本。

生成一次的成本由规划调用、候选搜索、引擎编译、渲染回放、设备测试和修复轮次组成。报告同时记录总成本与有效交付，避免只统计第一次生成耗时。

建议先各阶段串行跑通，再做互不冲突的缓存和并发。角色划分是职责模块，并不意味着必须同时启用多个 AI。

## 5. 自动调度与终止规则

每任务定义输入哈希、依赖、命令、超时、产物、退出码与验收。执行器统一管理子进程生命周期，超时后回收，保留日志；不能永久等待 Godot 窗口或设备连接。

伪流程：

```text
读取 RunManifest
选择依赖已通过的任务
若缓存哈希与工具版本匹配：复用
否则执行工具，收集退出码与证据
通过：保存检查点，运行下一任务
失败：分类 → 生成最小 patch → 重测受影响节点
缺必要环境/数据：记 UNVERIFIED 或 NEEDS_INPUT
达到重试/费用/时间上限：输出失败包并停止
全部必需 gate 通过：输出交付包
```

建议初始策略：每故障最多 3 次 AI 修复、每驻点最多 20 个几何候选，每轮关卡最多 2 次整层重规划；这些是可配置运行预算，不是质量定律。相同错误签名连续出现应停止盲目重试，保留冲突与最小复现。

恢复层级：数据错误改字段；摆放错误改局部布局；玩法错误改能力；资源错误改包装；性能错误按平台降预算；需求冲突返回规格。修复不能降低硬门槛、删除失败测试或默默放弃平台。

## 6. AI 的任务模板

每次任务给模型：当前阶段、用户原始需求、规范化规格、相关资源能力、目标文件、允许修改范围、失败证据、必须通过用例与成本上限。

要求模型返回：原因、最小变更、影响范围、要运行的检查。执行器实际运行后给它真实日志，不能接受模型自述“测试通过”替代工具结果。

职责可以拆为需求解释、关卡设计、机制实现、画面评估、失败归因五种提示模板。检索现有方法论时按机制读取章节，不每次把全部文档塞进上下文。

代码扩展可修改 `capabilities`；关卡规划默认只修改规格/IR；视听评估只提出问题；调度器控制文件范围和测试执行。这能减少一次修复同时乱改输入、关卡和评分。

## 7. 构建命令的职责

Godot 官方支持 CLI 导入、脚本与导出：[Command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)。下面只是待实现流水线的命令示意，`godot` 路径、项目、脚本和 preset 必须先存在：

```powershell
godot --headless --path game --import
godot --headless --path game --script res://tools/compile_level.gd -- --ir <absolute-ir-path>
godot --headless --path game --script res://tests/run_suite.gd -- --suite logic
godot --path game -- --test-run <run-id>
godot --headless --path game --export-release "Windows Desktop" <existing-build-directory>/game.exe
godot --headless --path game --export-debug "Android" <existing-build-directory>/game.apk
```

第四条需要真实显示/渲染环境和项目自定义参数解析；固定录像另设任务。导出目录预先创建，preset 名字必须匹配配置，模板版本与引擎匹配。每命令都校验日志与规定产物，而非只查退出码。

Android SDK/JDK 要按所锁 Godot 版本的官方要求安装并记录；首次优先 debug APK，release 签名信息由环境配置提供。签名凭据不写进规格和 AI 日志。参考：[Exporting for Android](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)。

Android 通过 ADB 安装、启动、采集 logcat/截图/性能与崩溃；外接鼠标测试覆盖真实 OS 输入，测试桥只验证玩法和可控回放。模拟器可测试生命周期与逻辑，不代替目标 GPU 和发热测量。

## 8. 工作流自身怎样验收

建立固定基准集：同资源不同机制、不同画幅、不同种子、资源版本变化、新机制、无解需求、缺设备和故障注入。

记录：硬门槛首次通过率、预算内最终通过率、每需求覆盖率、人工介入次数、错误检测率、错误定位时间、修复后回归失败数、双平台证据完整度。

首次验证可用 3 组描述 × 3 个种子，再扩展种子与设备矩阵。这个样本量只是启动规模，不能推出统计可靠的通用成功率。最终门槛按用户希望的自动化稳定性确定。

明确区分人工准备资源、首次底座开发、逐次游戏生产的人工介入。你的目标是资源准备后逐次生产尽量零介入；不能把隐藏的人工摆关卡排除在统计外。

## 9. 第一阶段 Definition of Done

- 用户描述生成有需求 ID 的 GameSpec，所有硬要求可验证。
- 引用标准资源自动生成正式场景，无需逐关人工摆放。
- 已支持机制自动组合，新机制有明确扩展与验证路径。
- 自动试玩、截图与日志能发现已定义的关键失败，并有限修复。
- Windows 和 Android 实际导出包可启动，平台验证状态清楚。
- 同资源至少三组不同机制版本证明复用；数据、代码、证据均可复现。
- 对无解/缺设备输出明确失败或未验证，绝不伪报成功。

下一个可执行任务：M0＋M1，先搭标准资源契约和鼠标射击实验室。完成后再用 M2 验证程序化场景算法是否真的满足光枪取景要求。
