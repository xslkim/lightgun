# 05 · 技术依据、选型和待验证问题

核对日期：2026-10-04。引用页面可能随 stable 分支更新；实际开发需锁定具体 Godot 小版本、模板和对应版本文档。本方案不将 master 文档所需 SDK 版本直接套用到某个已安装 stable 引擎。

## 1. 第一手技术依据

**可脚本化导入与构建**：Godot 提供 headless、import、script 与 export 命令；headless 无显示、使用 Dummy 音频。此能力使自动流水线可行，但本项目尚未运行这些命令生成游戏。[官方 CLI 文档](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

**Android 导出依赖**：需要符合引擎版本的 JDK、SDK 和模板，以及导出配置。发布包还有签名配置。本次读取的 stable 文档推荐 OpenJDK 17；实施前按锁定版本再核对 SDK 组件。[官方 Android 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)

**渲染器选择**：Mobile 面向较新移动设备，Compatibility 面向更广硬件；效果能力不同，切换需要验证。初期选择二者之一作为双平台基础，PC 高画质可后加 Forward+。[官方渲染器概览](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)

**资源标准格式**：优先使用 glTF 2.0/GLB。Godot 对 `.blend` 的导入通过调用 Blender 转为 glTF，需要 Blender。已准备资源阶段使用标准导出减少构建节点依赖。[官方 3D 格式说明](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)

**镜头投影和轨道**：Camera3D 提供屏幕射线与投影；PathFollow3D 支持沿路径移动。把镜头朝向、速度与战斗状态交由项目导演层组合，是本方案的设计推论。[Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)、[PathFollow3D](https://docs.godotengine.org/en/stable/classes/class_pathfollow3d.html)

**射线安全时点**：物理空间可能在输入回调中锁定，官方建议 `_physics_process()` 查询。采用带瞄准快照的输入队列，并实测延迟；不假设输入回调即时物理查询总是安全。[官方射线说明](https://docs.godotengine.org/en/stable/tutorials/physics/ray-casting.html)

**大量实例**：MultiMesh 减少大量相同对象的绘制开销，但整体裁剪，不能逐实例裁剪。因此按空间分组静态装饰，而不是全关一个实例集合。[官方 MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)

**光照烘焙**：LightmapGI 可用预烘焙光照，烘焙使用 GPU；无渲染 headless 节点不能被视为已满足烘焙环境。[官方 LightmapGI](https://docs.godotengine.org/en/stable/tutorials/3d/global_illumination/using_lightmap_gi.html)

**遮挡剔除**：静态简化遮挡几何可降低不可见场景开销，但需要 CPU 计算与实际收益验证。[官方遮挡剔除](https://docs.godotengine.org/en/stable/tutorials/3d/occlusion_culling.html)

**线程与复现**：活动场景树有线程安全约束；生成器纯数据计算与引擎节点修改分开。种子支持复现候选，但完整复现还需锁版本并保存 IR。[线程安全 API](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)、[随机生成](https://docs.godotengine.org/en/stable/tutorials/math/random_number_generation.html)

**后续硬件接入**：Windows Raw Input 提供分设备读取能力，Android InputDevice 提供设备信息；具体枪协议与绝对坐标仍需适配。它们不属于已确认的鼠标模拟首阶段验收。[Microsoft Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)、[Android InputDevice](https://developer.android.com/reference/android/view/InputDevice)

## 2. 决策记录

**D1：GDScript 主玩法**。与 Godot 场景/资源直接集成，减少跨语言与移动端链路复杂度；原生插件只承担确需的平台接口。不是断言其它语言不可行。

**D2：离线关卡编译优先**。先通过全部证据再打包，减少移动端生成开销。代价是内容变体需要预生成；运行时空间随机化以后另立目标。

**D3：JSON IR＋引擎 Resource**。JSON 方便 AI 与外部预检，Resource 提供运行时类型和引擎序列化。需要版本迁移与两端一致性检查。

**D4：模块＋遭遇模板＋屏幕约束**。能将现有设计规律转为可验证操作，资产直接复用。代价是资源语义入库和高质量模板需先建立。

**D5：CLI 为核心，MCP 可选**。控制链路可复现，避免 GUI 焦点影响自动化。缺少视觉捕获接口时实现项目自己的截图/遥测桥，而不让模型猜画面。

**D6：先鼠标后枪**。用户确认的第一阶段选择，可先验证开发自动化；保留输入抽象，后续不用重写玩法。鼠标通过不说明任何枪型已通过。

**D7：先用简单灯光**。M1–M2 先证明玩法与编译，复杂烘焙、流送和 PC 高画质在测量后增加。移动端性能从第一次导出开始跟踪。

## 3. 需要实验而非继续纸面争论的问题

1. 射击查询与渲染时序：移动敌人/镜头、不同物理 tick 下准星与命中偏差多大？比较消费时状态与快照回溯。
2. 标准资源是否足够语义化：随机抽取建筑、敌人和交互物，不手工改原模型能否完成包装、动画和碰撞？
3. 屏幕约束候选生成：三驻点模板的无解率、修复次数与构图差异，是否满足局部回溯预算？
4. 灰盒转正式美术：装饰、透明材质与 VFX 引入多少新遮挡错误，自动检测能否发现？
5. 新机制扩展：库外机制是否能通过独立场景并保持旧关卡回归？
6. Android 基线：目标 GPU、分辨率、输入和持续运行下的帧时间/内存，决定 renderer 与预算。
7. 复现：固定引擎/资产/生成器下 IR 是否一致，两个平台的行为差异是否落在容差内？
8. 自动修复：注入已知故障后能否在预算内定位并修复，是否存在为了通过测试而偏离需求？

这些实验都有对应 M0–M5 任务。先收集结果再决定是否引入复杂求解器、视觉机器人、多代理并发或运行时随机地图。

## 4. 原调研中需注意的数字与措辞

“经验反应窗”“当帧判定”“零配置所有硬件”不能直接作为技术保证。本方案保留设计意图，改成可配置目标、测量口径和设备支持矩阵。

章节时间表给出的是设计范围，实际波次数量与长度必须计算；驻点 20–45 秒与 4 波×20 秒不能自动同时成立。计分层的自然语言示意需变为明确数学规则。暂不修改原文档，避免覆盖其研究用途。

历史作品、玩家评价和商业数据不作为生成器正确性的证明；本项目实际运行的测试、画面和设备证据才是交付依据。
