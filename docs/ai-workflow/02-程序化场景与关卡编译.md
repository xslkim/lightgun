# 02 · 程序化生成场景与关卡

## 1. 为什么从镜头与遭遇反推空间

光枪玩家主要决策是“打哪个目标、何时开火、何时装填/防御”。一个地形连通、模型丰富的随机地图，仍可能让敌人太小、前摇被墙挡、镜头经过空无一物的走廊。空间生成必须服务于已定义的遭遇与取景。

推荐混合方法：**章节语法生成内容骨架，遭遇模板生成战斗语义，模块连接器生成空间，屏幕约束修正构图，局部采样摆放装饰**。LLM 生成规划和参数，程序计算几何与校验。

### 方法选择

- 模块化拼装：最适合第一阶段。房间、走廊、楼梯有标准连接点，组合可验证，真实资源直接复用。限制是资源需要连接契约，模块重复感需靠构图与装饰修正。
- 语法/模板生成：控制教学、升温、分支、BOSS 前休息，容易把现有文档变成规则。限制是模板质量决定上限，需支持参数变化与局部新模板。
- WFC：适合地砖、建筑外立面和小范围邻接一致性。局部邻接成立不保证主路线、镜头视线或救援事件成立；不作为主关卡算法。
- BSP/随机房间/迷宫：适合底层拓扑候选，光枪通常不需要探索大量不可见空间。生成后仍须重新解镜头与遭遇约束。
- 高度场/噪声地形：适合远景和室外环境，不能独立生成交战叙事与波次。
- LLM 直接输出所有坐标与整个 `.tscn`：适合小实验，长场景易出现尺度错误、资源引用漂移和无可解释修复。正式流程让模型输出 IR，由编译器装配。

这些是本项目的工程取舍，不是对算法能力的普遍否定。先使用最少算法完成闭环，再用实测失败证明需要更复杂的方法。

## 2. 三层生成系统

### A：章节与区域拓扑

生成带角色的有向图，例如入口教学 → 走廊练习 → 中庭救援 → 成功/失败支路 → 汇合 → BOSS。每节点定义空间类型、机制考验、驻点数量、期望时间和资源标签。

约束：起点到终点可达；每分支有结果反馈；分支默认汇合以控制内容量；允许循环时必须有访问次数或退出条件。不要默认把关卡图限制为 DAG 后又悄悄加入无限循环。

### B：交战驻点与构图

给每驻点生成镜头、主要战斗区域、入场遮蔽区、射击锚点、平民安全区、反馈禁遮区和转场出口。模板是空间和行为的组合，不只是“摆几个敌人”。

模板例：门口单兵教学、两侧优先级、多层掩体探头、平民精度、可击落投掷物、部件拆解 BOSS。参数包括深度、屏幕区域、目标尺寸、入場路径和窗口时长。

### C：资源实例与装饰

先连接建筑模块，再摆具有玩法语义的掩体与可破坏件，最后装饰。灯光与装饰不能修改已验证的射击规则；若挡住视线，回退这一局部装饰，重新做可见性检查。

装饰使用分区采样或 Poisson disk，约束类别、最小间距、地面法线、风格和预算。实例选型按资源标签与测量值匹配；禁止凭名字把不适合尺度的模型强行缩放进场景。

## 3. 一个驻点的生成顺序

1. 从章节目标确定“本点考验装填与目标优先级”，选两侧交战模板。
2. 选择可承载模板的房间模块，读取实际边界与连接点，确定可用战斗体积。
3. 选择镜头候选，约束高度、FOV、近远裁剪、镜头球形安全距离与出口方向。
4. 为目标分配期望屏幕区间；用深度与投影求世界锚点，落到可站立区域。
5. 选择敌人资源与动画，生成从遮蔽区到战斗锚点的路径，检查碰撞与最短时长。
6. 根据出现、可读、可射击、攻击时刻编排波次，计算弹药与有效窗口。
7. 加入有限的可破坏物、补给、平民或分支靶，重新检查遮挡与规则冲突。
8. 放置灯光和装饰，渲染关键帧与连续片段，通过后保存场景和生成报告。

若没有有效房间/镜头组合，回到第 2 步更换候选；若只是装饰遮挡，回到第 8 步。局部失败不重写整个章节。

## 4. 连接点与几何约束

模块连接点包括本地位置、朝向、接口类型、宽高、楼层、可连接标签、封口方案。选中连接后计算变换，让两个接口位置重合、法向相对；只接受允许的旋转与缩放。

广相 AABB 用于快速排除候选，OBB/碰撞形状用于确认。记录允许重叠区域：门框与墙可能合理重叠，敌人身体与实心墙不可以。全部禁止 AABB 相交会错误拒绝正常模块。

室内优先平面与明确坡道，室外按高度采样贴地。敌人使用指定入场/战斗路径时可不依赖全局导航；需要追击、绕路或移动平民时再生成导航并确认路径到达。不要把全场景 NavMesh 烘焙设为每次装饰改变后的默认成本。

建筑碰撞和射击碰撞分开：小装饰若可阻挡射线，必须在画面上具有可识别实体；一面透明玻璃的阻挡/破坏规则需要明示。

## 5. 屏幕约束与可读性求解

### 两类角度不能混用

相机 FOV 描述虚拟世界投影；玩家站距与屏幕物理尺寸描述真实观看视角。设画面有效物理高度为 H、站距为 D、目标占有效画面高度比例为 q，中心附近目标的观看视角近似为：

`theta = 2 * atan(q * H / (2 * D))`。

它只适用于正对屏幕等假设，偏轴和边缘目标应更精确计算。未知 H、D 时使用可选客厅/桌面配置或屏幕像素阈值，必须注明代理指标，不能把 q=5% 宣称为所有设备都达到某个观看角度。

虚拟投影初值：目标高度 h、相机深度 z、垂直 FOV 为 F，则中心附近画面高度比例约为 `q = h / (2*z*tan(F/2))`。这只是锚点初始化；最终使用 Camera3D 实际投影与目标可射击部位测量。FOV 轴向受 `keep_aspect` 影响，不能在所有画幅直接把 `fov` 当成垂直角度。依据：[Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)。

### 生成器应计算什么

- 可射击部位的屏幕包围区域，而非整个模型 AABB 的投影面积。
- 屏幕可见比例、最近遮挡物、弱点面积、与其它目标的屏幕重叠、HUD 覆盖率。
- 从最早可识别/可射击时刻到攻击生效的连续窗口，包含入场、转头、探头和镜头移动的影响。
- 瞄准移动距离、能力配置中的反应时间、武器射速与装填时间，筛查同时威胁是否不可处理。

射线抽样用于快速几何可见性筛选；GPU ID/depth mask 用于实际可见像素；美术截图检查轮廓、明暗与特效遮挡。几何可见不等于人眼能读懂，三个层次必须区分。

在驻点关键时刻与整个危险窗口采样；接近遮挡边界时增加采样密度。离散采样可能漏掉短暂遮挡，应设置时间/空间裕量，并通过连续回放补查。规则检查通过并不等于得到形式化“永不遮挡”证明。

### 硬约束与软目标

硬约束来自 GameSpec：有可打窗口、伤害前已预告、镜头不穿碰撞、每必杀目标可达、关键菜单在安全区。违反任一项先淘汰。

软目标包括构图层次、屏幕分区均衡、相邻镜头区别、背景变化和反馈强度。合格后才按加权分排序；“画面好看”的高分不能抵消一个不可击中的敌人。

候选搜索先用模板参数范围和有限回溯，必要时增加约束求解器。每次给出失败位置与冲突约束；第一版不必引入大型数学求解框架。

## 6. 镜头、波次和事件的编排

推荐镜头状态：`Moving → Settling → Combat → Resolving → Moving`，分支与演出进入独立子状态。移动轨道用 Path3D/Curve3D，PathFollow3D 负责位置；目标朝向由独立 look-at 曲线/关键帧控制，避免路径切线旋转导致突然甩镜。路径跟随能力依据：[PathFollow3D](https://docs.godotengine.org/en/stable/classes/class_pathfollow3d.html)。

事件以依赖和局部时间定义：`camera_settled → entry_cue → spawn → targetable → telegraph → attack/interrupt → resolved → gate_release`。`at_ms` 默认相对本驻点“落位完成”计时，跨波次依赖显式写出。

不把所有事件写成绝对全局秒数，否则玩家早清/晚清都会破坏后续编排。演出时间轴可用 AnimationPlayer；战斗推进由事件与条件主导。

波次释放需定义敌人终态集合，包括击杀、逃离、缴械、不可恢复失败等；根据机制选择是否需要清空弹道。平民不能误计为必杀敌人，掉落物不能让清场永不完成。

每个闸门有超时政策：计时失败、强制撤退、释放演出或报错。Watchdog 不能静默把软锁当成通关；它记录失败证据，测试构建直接判失败。

命中、死亡、救援、分支和波次完成均附 `event_id`，幂等处理；防止重复 signal 开两次门、发两次奖励。分支只能提交一次，提交时记录依据与兜底结果。

## 7. Godot 场景编译器

建议节点层级：

```text
LevelRoot
  EnvironmentChunks       建筑/装饰/灯光/碰撞
  CameraRig               Path3D / 跟随 / Camera3D
  EncounterDirector       驻点和事件状态机
  SpawnAnchors            Marker3D
  Actors                  敌人/平民/投掷物
  Interactables           可破坏物/选路靶/补给
  Feedback                音频/VFX
  DebugOverlay            视线/窗口/事件轨迹
```

编译过程：加载 IR → 验证引用 → 实例化包装场景 → 应用变换 → 连接稳定 ID → 创建轨道与碰撞 → 序列化 Resource → 保存 PackedScene → 导入重载 → 测试。

动态创建节点后必须正确设置 `owner` 才能打包保存；嵌套实例内部遵循场景所有权，不随意展开重写。资源路径与 UID 交由引擎保存并验证，禁止模型编造 UID。生成文件与原始资产、稳定代码分目录，明确谁可覆盖谁。

推荐输出 `game/generated/levels/<level_id>/` 与旁侧生成清单；手工覆盖放 `game/overrides/`，以稳定实例 ID 应用。修改种子不能改变已有实例的身份语义。

后台线程可计算纯数据，场景树修改在主线程执行。Godot 官方明确活动场景树的线程安全边界，见 [Thread-safe APIs](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)。

## 8. 开发时生成与运行时生成

第一阶段选择开发时生成、校验、保存和打包。好处是能提前渲染全关、缓存导入和光照、复现错误、保证移动端启动时间。用户最终看到的是普通 Godot 游戏，不需要 LLM 或编辑器在设备上运行。

运行时只允许已测过的变体：敌人组合、装饰选择、受限节奏扰动。改变空间拓扑、破坏结构或灯光时，不能沿用不匹配的导航、遮挡或光照烘焙结果。若以后做 Roguelite，另建运行时生成质量门槛。

固定种子还要锁定生成器版本、资源哈希、排序规则与引擎。随机子流按模块/驻点/装饰隔离，避免加一个灯影响所有刷怪。保存最终 IR 才是权威复现输入；种子不能保证跨引擎版本、跨平台物理浮点行为完全一致。Godot 随机生成基础见 [Random number generation](https://docs.godotengine.org/en/stable/tutorials/math/random_number_generation.html)。

## 9. Android 性能必须进入生成约束

每平台有独立画质预算：可见三角形、材质/绘制调用估计、贴图内存、活动骨骼、灯与阴影、透明覆盖、粒子、尸体和预加载内存。初值依据基准场景标定，不能用固定“多少面就能 60 FPS”代替实机测量。

重复静态装饰按空间 chunk 使用 MultiMesh；不要全关合成一个大 MultiMesh，也不要默认用它承载所有独立动画/伤害对象。MultiMesh 的实例缺少逐个视锥裁剪能力，见 [MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)。

按驻点群分块预加载，记录加载尖峰；室内可加入简化遮挡几何并做收益对比。遮挡剔除有 CPU 成本，自动烘焙不覆盖所有节点类型，见 [Occlusion culling](https://docs.godotengine.org/en/stable/tutorials/3d/occlusion_culling.html)。

静态光照可离线烘焙；烘焙任务需有 GPU 的构建节点，不能假设 headless 无渲染流水线能完成。第一切片先用简单光照把玩法打通，后续再验证 LightmapGI 的自动烘焙、资源包含和视觉结果。依据：[LightmapGI](https://docs.godotengine.org/en/stable/tutorials/3d/global_illumination/using_lightmap_gi.html)。
