# 01 · 从描述到双平台构建

## 1. 总体流水线

```text
用户描述 + 已入库资源 + 平台配置
  → GameSpec（机制与验收）
  → CapabilityPlan（复用/组合/新机制）
  → ChapterPlan（教学、节奏、分支）
  → LevelIR（空间、镜头、波次、事件）
  → 静态预检 → Godot 场景编译 → 灰盒试玩
  → 资源装配 → 画面/音频检查 → 机器人试玩
  → PC/Android 构建与设备验收
  → 结果包：源码、构建、规格、回放、报告
                    ↑ 失败定位 → 最小修复 → 相关回归
```

这是一条有产物、有检查点的流水线。可由一个 AI 顺序执行不同职责，未来也可并行；不依赖同时运行多个模型或某个 MCP 服务。

## 2. 九步操作规程

### S0：环境和资源入库

输入：资源目录、目标平台、可用设备。输出：`asset_manifest.json`、`environment_report.json`、版本锁和资源预览。

操作：识别文件与内容哈希，Godot 批量导入；测量包围盒、材质、动画和骨骼；生成轻量包装场景；绑定语义标签与连接点。区分“渲染背景”“碰撞环境”“可射击部件”“敌人”“反馈资源”。

通过条件：被本次计划引用的资源全部导入成功；必需动画/碰撞/连接点满足契约；平台工具齐备或明确未验证项。资源库中无关资源异常不应阻塞整个游戏。

失败：自动补包装节点、简化碰撞、映射动画；缺核心动画/连接点且无法推断时，输出资源缺口。未经声明的缺资源不能静默用方块替代最终交付。

### S1：自然语言需求编译

输入：用户描述、设计方法论检索结果、资源能力表。输出：`game_spec.json`、`assumptions.json`、`acceptance.json`。

提取：玩家动词、输入、镜头范式、胜败、敌人、武器、关卡量、分支、计分、平台和画面目标。每条需求生成稳定 ID，并链接到规则和验收，例如 `REQ-RELOAD-001 → weapon/reload → TEST-RELOAD-BOUNDARY`。

对“恐怖但轻松”“90 秒且含长演出”“能躲避但永远不花代价”等冲突生成可解释决策。缺少风格细节可使用登记默认值；缺失会改变核心玩法的信息需要用户回答。自动开发运行允许先采用默认配置完成候选版本，报告中保留假设。

通过条件：每个硬性要求有可观察结果与判定；禁止“好玩=true”或“与某经典一样”成为唯一验收。用户以后修改描述，只改对应需求和受影响产物。

### S2：机制能力规划

输出：`capability_plan.json` 和任务 DAG。

将要求分为：已有模块参数化、已有模块组合、新模块实现。组合也要做交互测试，例如慢动作与装填、掩体与计时、人质与爆炸范围。核心玩法模块固定接口，禁止为一关复制整套代码。

新模块按“接口契约 → 独立小场景 → 反例测试 → 回归 → 入库”处理。无法稳定实现时交付失败证据；未经用户允许，不将新机制偷偷替换成库内近似机制。

### S3：章节与节奏计划

输出：`chapter_plan.json`，描述教学→练习→组合→高潮→收尾，以及可选支路和汇合点。

以交战驻点为内容单元，注明每点打谁、从哪来、结束后去哪。分别记录参考玩家耗时、最短耗时、超时上限和演出时间；清场驱动的关卡不能假定所有玩家都按固定秒数完成。

通过条件：所有要求至少有一次教学或演示，有一次实际考验；每个分支可达终点；章节时间范围自洽。未实现的机制不能进入量产排程。

### S4：LevelIR 生成与约束求解

输出：一组有种子和版本号的候选 `level_ir.json`，以及 `constraint_report.json`。

先生成空间拓扑与交战构图，再放置模块、刷怪路径和装饰。硬约束筛选：镜头不可穿墙、敌人有可射击窗、波次可结束、分支可达、预算估计不过界。软目标排序：画面层次、镜头变化、节奏、空间多样性。

通过条件：所有硬约束成立，软指标超过项目阈值。无解时报告冲突集合，例如“所需敌人规模＋指定视口＋指定安全区”无法同时成立；逐层修复，不无限随机抽取。

### S5：编译与灰盒验证

Godot 编译器把 IR 转为 `.tscn/.tres`，生成碰撞、路径、Marker、事件调度与调试视图。运行固定输入、规则机器人和状态机测试。

通过条件：导入和脚本可运行；核心机制、波次释放、分支、死亡重试全部通过。灰盒替代只适用于这一阶段，报告显示所使用的替代物。

先在灰盒发现“救人触发门但门永不开”的逻辑错误，再使用完整美术，避免每次修复都重新生成或导入全部资源。

### S6：正式资源装配与视听检查

把正式模型、动画、音效、HUD 和 VFX 绑定到已验证的灰盒。输出关键帧、短片、可见性报告、音频事件/采样报告。

通过条件：动画与规则时序对齐；画面内关键目标可识别；准星与命中一致；HUD 不遮目标；关键声音存在且可听；替代资源清单为空，或全部经过明确接受。

装饰调整后必须重新检查视线与性能，不能因为灰盒通过而跳过正式画面检查。

### S7：自动试玩、调参和修复

输入：固定种子矩阵、机器人能力配置、脚本回放、视听报告。输出：试玩录像、JSONL 遥测、问题列表、参数变更和回归结果。

完美机器人用来查软锁；带反应时间、瞄准速度、误差、弹药策略的机器人用来筛查压力失控；盲点机器人用来覆盖“不打、乱打、误击、退出重进”。视觉机器人或截图评估用来检查信息是否真的出现在屏幕上。

通过条件：硬测试全部通过，软评分和样例片达到项目门槛；真实玩家体验尚未测量时标注未验证，不虚构留存或好评。

### S8：双平台构建与交付

输出：Windows 构建、Android APK（需要时 AAB）、源码、版本清单、构建哈希、测试报告、回放入口。

必须启动实际导出包验证资源包含、启动场景、设置保存、存档、重试；不能只在编辑器里测试。Android 还需设备上的鼠标/测试输入、生命周期和持续运行检查。没有实机时可以交付 APK，但 Android 输入与性能状态为 `UNVERIFIED`。第一阶段不要求实体光枪证据。

通过条件：所请求平台的必要证据齐全。自动构建不自动等于商店发布；上传/发布由后续明确任务定义。

## 3. 六种关键契约

### GameSpec：游戏要做什么

字段：`schema_version`、`game_id`、`platform_profiles`、`requirements`、`mechanics`、`camera_mode`、`input_profiles`、`content_plan`、`quality_targets`、`assumptions`。

机制条目定义参数、前置条件、事件输入、状态输出、可观察结果。时间采用整数毫秒；空间采用米；画面坐标采用归一化有效视口坐标。用户描述与规则文本同时保留，方便判断需求解释是否跑偏。

### AssetManifest：有什么能用

每资源：稳定 ID、文件与哈希、类型、风格、尺寸、原点、轴向、允许缩放范围、连接点、碰撞、动画映射、平台替代版本、粗略成本和预览。

原点为地面中心或指定 socket；Godot 使用 Y 向上、相机朝本地 -Z。导入时明确转换，不让模型凭文件名猜单位。资源能力声明必须经过实际导入检查。

### LevelIR：具体关卡如何实现

包含：语义区域图、实例变换、轨道与取景、驻点、锚点、敌人入场/战斗路径、波次、事件条件、分支、检查点、装饰禁布区和预算。

IR 是 JSON 中间表示，便于 diff 和静态验证；运行时可编译为强类型 Godot Resource。JSON 不携带任意可执行代码，机制扩展经独立代码流程落地。

### MechanicContract：扩展模块如何接入

明确能力 ID、版本、依赖、输入事件、状态、输出事件、序列化方式、组合冲突和验收用例。所有伤害、分数、装填、镜头切换均通过明确命令/事件接口，禁止各脚本随意改全局血量。

### Evidence：为什么可以判断成功

每项证据有 `requirement_id`、`test_id`、构建与资源哈希、种子、设备、输入配置、结果、日志、录像/截图位置。证据不跨构建复用；只对可证明不受变更影响的测试保留缓存。

### RunManifest：如何继续未完成任务

记录运行 ID、当前阶段、产物哈希、引擎/编译器版本、任务状态、失败类型、重试次数、成本和下一任务。暂停或重启从检查点继续；相同输入应复用已有结果。

## 4. 数据和代码的分工

现有武器射速变化、敌人血量变化、驻点构图、分支条件应走数据；新伤害模型、新输入语义、全新 BOSS 状态协议走代码。避免把一切塞进无类型 JSON，也避免每个关卡生成数千行新脚本。

建议 Godot GDScript 实现主玩法与编译器；Python 管资源索引、预检、任务执行和结果聚合。原生输入仅在平台确需时使用 GDExtension 或 Android 插件。

模块边界确定后再做图形关卡编辑器。第一版只需 AI 可读写的数据、命令行入口与 Godot 调试预览；人工拖拽不是自动化链路的必需环节。
