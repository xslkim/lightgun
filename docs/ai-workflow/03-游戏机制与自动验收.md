# 03 · 玩法底座、机制扩展与验收

用户已确认第一阶段使用鼠标模拟。本章的实体光枪与双人原生输入部分用于说明后续扩展边界，不是首阶段必须实现的任务；首先实现鼠标、回放和单人玩法。

## 1. 稳定模块与职责

**InputHub**：设备枚举、玩家绑定、校准、归一化指向与动作事件，适配鼠标/触摸/回放/真实枪。状态含 `tracking_valid`、`offscreen`、设备 ID、玩家 ID、时间戳与序号。

**ShotResolver**：扳机事件带瞄准快照，转换到正确视口和相机射线，查询可射击对象，输出 ShotResult。准星与射线共享坐标转换，禁止各自维护比例。

**WeaponController**：弹匣、射速、装填、特殊武器、空仓、输入互斥与事件。用明确状态转移处理装填，不能每次离屏都重复播放或重新开始计时。

**DamageSystem**：命中部位、伤害、霸体、打断、死亡与共享血量；单个 shot_id 对同一目标只结算一次。武器贯穿/范围伤害用明确扩展策略。

**ActorController**：普通敌人状态机与路径，平民救援/误伤/死亡状态机，投掷物状态机，BOSS 分阶段子状态机。所有攻击可暂停、可清理、可恢复。

**EncounterDirector**：镜头、驻点、波次、分支、超时和演出编排。它消费事件，不读取所有敌人的内部动画状态来猜进度。

**ScoreService**：命中、击杀、部位、救援、误伤、连击与结算。公式显式确定，例如 `基础得分*连击倍率+事件奖励-罚分`；原调研中的概括公式不能不加辨别直接实现。

**Feedback/HUD**：开火、命中、弱点、打断、装填、受伤、救援和阶段反馈；身份色与战斗状态编码区分；菜单同样走输入接口。

**Session/Save**：暂停、死亡、重试、设置、checkpoint 和规则版本。保存的是明确状态，不是随意序列化整个场景树。

**Telemetry/TestBridge**：输入注入、状态快照、断言、录屏、事件 JSONL 与测试退出码。测试桥仅在测试构建可用，产品 UI 不展示这些工程概念。

## 2. 命中判定中的时间一致性

Godot 官方说明物理空间在 `_input()` 时可能被锁定，查询宜在 `_physics_process()` 中执行：[Ray-casting](https://docs.godotengine.org/en/stable/tutorials/physics/ray-casting.html)。因此不能在方案中把“任意输入回调里立即查物理，永远零帧延迟”作为既定实现。

第一版采用：输入事件进入短队列，保留按下时的瞄准与相机状态，最早安全的物理 tick 消费；枪声/开火提示可立即响应，命中确认在判定完成后触发。记录输入收到→消费→命中→渲染的时间，测量是否满足项目延迟目标。

选择物理碰撞或独立解析的射击 hitbox 后，明确判定是“输入时状态”还是“消费时状态”。第一版默认消费时状态，队列不超过一个安全 tick，并测试移动敌人偏差；若要求严格还原输入时画面，需缓存目标姿态做回溯或独立 hitbox 查询。这是底座专项验证，不由 AI 口头承诺解决。

Hitbox 可以比可见部位略宽以容错，但不能透墙、不能把平民后的敌人优先选中。所有辅助策略在输入配置中显式登记；比分比较时配置必须固定。

## 3. 输入的跨平台边界

标准事件：`AimSample`、`TriggerPressed`、`TriggerReleased`、`ReloadRequested`、`CoverChanged`、`PauseRequested`。Trigger 附同设备、同序列的有效瞄准快照，追踪失效不得自动射到上一次位置。

屏幕→窗口→内容区域→实际渲染 Viewport→Camera3D 的变换链需要处理 DPI、黑边、缩放、全屏切换、旋转和外屏。归一化坐标以有效内容矩形为准，原始出界值另存；不要先钳到 [0,1] 再丢掉离屏信息。

明确离屏事件优先，坐标推断带迟滞；边缘抖动、焦点丢失和追踪丢失不能当装填。手机触摸没有枪口离屏，使用装填按钮或等价手势；不伪造光枪离屏输入。

Windows 双枪需分设备坐标与按钮配对，不能用系统合并鼠标光标测试替代。Raw Input 提供按设备区分与枚举的基础能力，但具体枪上报相对还是绝对坐标、厂商软件是否合并输入需要实测：[Raw Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)。相对位移积分无法保证恢复真实绝对枪口方向，仅作受限降级方案。

Android 原生设备来源、ID 与事件接入可通过插件扩展；OS、USB/Bluetooth、厂商协议与外屏映射共同决定能否使用。Android 有 InputDevice API 不等于 Godot 已支持所有光枪：[InputDevice](https://developer.android.com/reference/android/view/InputDevice)。

多枪和真实后坐力按具体设备验收。软件输出语义事件即可；实际执行器适配必须遵循设备能力与频率限制，不把原调研中未核实的频率当通用规格。

## 4. 一个新机制怎样自动加入

以“击中敌人手臂使其掉枪，转为逃跑；掉枪时奖励分，击杀另计”为例：

1. 从描述生成状态、事件和要求：手臂可射击；仅持枪状态缴械；不得重复奖励；逃跑有终态；驻点允许缴械后释放。
2. 检查已有部位伤害和逃跑能力，组合能力而非复制敌人脚本。
3. 需要新逻辑时建立 `DisarmCapability`：输入 HitResult，输出 Disarmed 事件，引用动画和掉落物配置。
4. 自动创建独立小场景，验证打手臂/躯干、连击、多玩家同 tick、被击杀后命中、暂停重试。
5. 回归普通敌人死亡、评分和清场；通过后将该能力版本登记到库。
6. LevelIR 引用能力，在正式关卡中验证动作、可见性与节奏。

新机制的成功标准包括交互影响。代码可编译但让所有普通兵永久硬直，仍然失败。

## 5. 时间、暂停和恢复

至少分三时钟：真实单调时钟（输入/性能）、游戏逻辑时钟（敌人、装填、计时）、演出时钟（慢动作/镜头）。GameSpec 必须决定慢动作是否影响攻击、装填、计分计时和射速，不能随便全局乘一个 time_scale。

敌人状态机：`Entering → Ready → Telegraph → Attack → Recovery`，允许特定状态进入 `Stagger/Disarmed/Dead/Escaped`。打断预算按敌人记录，霸体段有对应可见表现。弱点状态与攻击状态分开，否则 BOSS 发光会混淆“可以输出”和“即将受伤”。

重试恢复 checkpoint 时，销毁旧演员/投掷物/回调，清空队列，重置导演、随机子流和分支，按规则恢复玩家血量/弹药/分数。不能残留上次攻击 Timer 在新场景扣血。

双人同 tick 输入使用稳定排序策略，例如 tick、事件序号、玩家 ID；记录规则，避免靠 signal 回调偶然顺序决定击杀归属。真正同时命中的公平性策略由 GameSpec 指定。

## 6. 自动验收的五层证据

### L0：结构与静态规则

检查数据格式、资源引用、图可达性、事件依赖、条件类型、参数范围、窗口初值与预算估计。示例预检程序只覆盖其中一小部分，不代表完成全关卡验证。

### L1：规则与状态机

验证空仓不射击、一次装填只补一次、掩体时不能输出、打断只发生在允许状态、BOSS 弱点关闭免伤、同射击不重复扣血、多玩家分数独立、暂停与恢复时间一致。

用边界时刻和事件序列验证：弱点关闭前后、死亡前后、装填完成同 tick 输入。测试从 GameSpec 的行为契约生成，并保留稳定回归案例；不能所有测试都与新实现一起随意改写。

### L2：完整关卡行为

规则机器人从正式 InputHub/WeaponController 注入输入，允许读取世界状态以规划，但不直接改血量或触发通关。完美机器人应能走完所有必需路径；从头挂机应触发定义的失败/退出，不能永远等待。

覆盖所有支路、不同救援结果、选路超时、死亡重试、暂停、丢焦点、设备断连和双人加入/退出。固定种子回归与新种子探索分开；新种子发现错误即加入永久回归集。

### L3：实际视听结果

记录关键事件前、中、后的截图/短片；采样射击部位 mask、遮挡、准星、HUD、画幅和 VFX。音频不仅检查播放事件，还检查对应片段与混音是否存在/被盖住。

模型视觉评审只能作为软判断。发现疑似不可读场面时用可见区域、前摇记录和声音证据复核。不能让同一生成模型的一句“看起来很好”覆盖硬失败。

### L4：导出包与实机

在 Windows 导出包运行鼠标、回放和菜单/存档测试；在 Android 实机运行外接鼠标或测试桥，检查后台/前台、屏幕变化、音频恢复、资源加载与内存。触摸作为可选输入；真实枪留到后续适配阶段。

性能记录 CPU/GPU 帧时间、p50/p95/p99、加载卡顿和内存，不用平均 FPS 单独验收。持续运行要足够暴露发热降频，例如先用 15–20 分钟压力片段，长度后续按目标设备标定。帧时间目标依设备、刷新率与项目配置确定；60 FPS 对应约 16.7 ms 仅是预算换算。

Headless 使用 Dummy 音频和无显示运行，适合逻辑与导入；不能验证真正渲染帧时间、声音体验或端到端输入延迟。录像固定帧率可用于检查编排，不能当实时性能测量。

## 7. “可通关”与“好玩”的区分

带误差机器人拥有明确参数：反应时延、瞄准速度、目标选择、射击间隔、误差、装填策略。用多个能力档比较波次压力、预期受击、失败集中点和资源紧缺。

这些参数是合成玩家模型，不能直接推出真人首关完成率、留存或好评。第一阶段自动化的目标是消除软锁、不可读、不可完成和明显节奏问题，筛选出值得玩的版本。

若坚持整个生产过程无人介入，可以用已通过真人标定的模板和机器人分布作为质量代理，但报告只能说通过该代理，不能声称已证明所有玩家都觉得好玩。后续少量真人样本反过来校准模板，而不必每次手工制作关卡。

## 8. 建议首批验收用例

- 瞄准覆盖：中心、四角、边缘、黑边、多画幅、显示缩放；点击准星位置与命中对象一致。
- 装填：贴边抖动不触发，明确离屏触发，追踪丢失不触发，暂停不重复补弹。
- 敌人：首次危险前已可读，打断有效且有限，不可射击时不会无预告伤害。
- 关卡：清场前不走，最后目标逃离/缴械能结束，所有支路到汇合，超时按规则处理。
- BOSS：弱点窗口两侧边界、阶段切换、重复事件、死亡后攻击残留。
- 双人：同目标共享伤害、各自弹药分数、同 tick 归属、断连与重新绑定。
- 发布包：导出后缺资源、设置持久化、存档迁移失败提示、Android 切后台恢复。

硬性用例一项失败就不输出成功状态；软评分不足进入有限调参；缺实机保留未验证状态。
