# 01 · 系统架构与数据契约

本篇定义模块边界与数据含义。设计依据见 [design](../README.md#2-文档组织与阅读顺序)，场景生成算法见 [02](02-场景与关卡生成方法.md)，执行顺序与验收见 [03](03-开发工作流与验收.md)。下面是待实施架构，不代表这些模块已经存在。

## 1. 两层系统

**开发工具链**把资源和描述转换成可运行项目：读取规格、规划能力、生成关卡数据、调用 Godot 保存场景、运行测试并汇总结果。

**游戏运行层**消费已经生成的数据：处理输入、执行武器与敌人规则、协调镜头和波次、显示反馈、处理胜败和重试。

第一版使用 GDScript 实现玩法与引擎内场景编译，Python 负责外部数据预检和任务调度。生成器不直接操控游戏中的血量或通关状态；测试输入也须经过正式玩法接口。

## 2. 开发工具链模块

### 资源目录

职责：将已有资源整理成可实例化、可查询的能力目录。

自动提取文件、尺寸、材质和动画等可测信息；行为标签、弱点、入口、连接点等无法可靠推断的信息，来自资源包约定或一次性确认。AI 可以建议标签，但建议不能自动变成已验证能力。

资源检查还测量部位投影、动作提示和材质/特效的实际表现，供风格配置标定使用。风格标签用于筛选候选，不能替代可读性或性能检查。资源换风格后是否改变功能，按 [DES-PRESENT-07](../design/03-视听反馈与交互规范.md#des-present-07) 分类。

只要求本次游戏使用的资源满足契约，不要求整个资源库都经过完整加工。优先采用标准场景与 GLB；Godot 支持 glTF，直接导入 `.blend` 需额外调用 Blender。[官方格式说明](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)

### 规格与能力规划

职责：把描述转换为行为规则、参数、内容要求与验收条件，并区分已有能力、新组合和新实现。

规格必须保留用户原话与默认假设。例如“装填期间不能开火”需要形成明确规则，“有压迫感”需要转为待评估的节奏目标。缺少决定核心行为的信息时需要澄清；可以采用默认值的细节则记录默认值并继续。

### 关卡生成器与场景编译器

生成器输出关卡中间数据（LevelIR），负责空间、取景与事件安排；编译器负责资源实例化、路径、碰撞和场景保存。两者共享版本化格式。

编译器不自行改变设计：如果缺资源或不支持某种事件，应报告错误，不默默换成别的机制。生成文件与稳定代码、原始资源分目录管理，生成文件可重建。

### 验证与执行器

验证器检查数据、玩法行为与实际视听结果；执行器启动引擎、构建和设备任务，记录日志、产物与退出状态。验证判定不依赖 AI 自述“测试通过”。

首版只需要一个 AI 顺序调用这些工具，不要求多代理、MCP 或复杂调度服务。

## 3. 游戏运行层模块

### 输入与武器

玩家注册模块维护稳定 `player_id`、输入源绑定、参与/失能/连接状态；输入适配器将每路鼠标模拟、其它已选设备或回放转换为带玩家身份的统一动作：瞄准、开火、装填、暂停。暂停属于会话请求，不只暂停某个玩家。每位玩家独立拥有武器与生命组件，只有指定共享资源由团队模块管理。

开火事件带唯一 ID、`player_id`、输入源、瞄准位置、时间和尝试标识。瞄准位置统一转换到有效内容区域，再进入 Godot 视口；处理黑边、窗口缩放和画幅，各玩家准星使用同一套转换。无效/画外指针不产生边缘射击，菜单与战斗输入分上下文。首阶段如启用装填，按玩家映射按键，不依赖模拟“枪口离屏”。

双人自动测试使用两路独立虚拟指针，可分别注入与回放；真实试玩另有设备适配与验收。不能仅依据 Godot 事件的 `device` 字段就宣称普通双鼠标已可独立瞄准，需要在目标版本和平台做小规模验证。[Godot 输入事件文档](https://docs.godotengine.org/en/stable/classes/class_inputevent.html)

如选双鼠标，Windows 可研究分设备 Raw Input，Android 可研究原生 InputDevice 及输入事件桥接；这些是待验证的适配路径，不是 Godot 项目已经支持的功能。普通鼠标的相对位移按各自速度配置更新虚拟准星，真实光枪将来接绝对坐标适配器，两者不混淆校准语义。鼠标＋手柄等方案也经独立适配器进入相同动作契约。[Windows Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)、[Android InputDevice](https://developer.android.com/reference/android/view/InputDevice)

### 射击、伤害与敌人

射击模块在合法时点查询环境和目标，输出命中对象、部位、位置与 shot_id。伤害模块决定伤害、打断和死亡；敌人模块拥有行为状态与路径，并消费这些结果。

结果保留 `player_id`。同一物理步内的合法射击为一个结算批次，先收集命中候选，再按输入时间、玩家 ID、射击 ID 的稳定顺序结算，并记录本批次起始时仍有效的目标。按双人规则区分正常伤害与本批次过量命中，目标清理在批次结算后执行；一次死亡、任务完成与团队奖励只发一次。批次间的无效目标不冒充有效命中。

攻击事件明确受影响玩家集合，生命组件分别消费结果；攻击目标选择、失能后是否重选与对应提示由能力契约定义。不能用共享屏幕隐式推导“所有人同时受伤”。

同一射击对同一目标的同一伤害结算只执行一次。贯穿、范围伤害、护盾等需要显式策略，不能靠碰撞回调数量决定伤害。敌人类型差异优先通过组件和数据表达，新行为再扩展代码。

### 关卡导演

统一拥有镜头阶段、驻点、波次、任务结果、分支和推进条件。其它模块向它提交事件；它根据关卡数据决定何时进场、何时结束、下一点去哪里。

平民救援、BOSS 阶段或选路属于可选任务模块。它们提供结果，导演消费结果；不让任务脚本私自切镜头，也不让镜头脚本自行判断任务是否成功。

### 会话与表现

会话模块处理开始、暂停、失败、重试和结算。首版以驻点起点作为重试边界，按规格重建该点的明确初始状态；资源恢复策略见 [DES-COMBAT-04](../design/01-核心玩法与战斗规则.md#des-combat-04)。任意时刻保存所有动态状态不是首版要求。

团队模块汇总共享任务、参与人数和双方生命状态，按 [DES-COMBAT-07](../design/01-核心玩法与战斗规则.md#des-combat-07) 决定继续或失败。加入退出与输入断开由会话处理，人数切换只在约定边界应用已验证配置；共同重试恢复双方和世界快照，不让 P1 重试而 P2 留在旧尝试。

表现模块订阅开火、命中、打断、受伤、装填等事件，驱动 HUD、动画、音频与特效。计分按需求加入，但核心规则不由浮字或动画是否播放来决定。

测试桥提供输入注入、状态读取、事件日志和截图，仅用于测试构建。它可以读取内部状态作断言，不能通过直接扣血或触发通关绕过规则。

## 4. 四类核心数据

以下规定信息类别与语义，具体 JSON Schema 在实施时锁定。现有 `tools/workflow-example` 是简化演示，并未完整实现本节格式。

### GameSpec：游戏规格

包含版本、平台与输入配置、支持的 1–2 人模式与双人必需要求、玩家/团队规则、风格配置引用、用户要求及稳定 ID、所选设计规则 ID 和文档版本、机制参数、胜败与重试、关卡规模、验收条件和假设。记录基线、默认建议和可选机制的选择，以及用户覆盖或例外；运行时只消费具体规则，不读取设计散文自行推断行为。

每条硬要求连接到设计依据、实现位置和测试，例如：`REQ-RELOAD → DES-COMBAT-02 → Weapon → 装填期间开火测试`。设计 ID 定位到该节，具体行为仍以本次需求为准；引用整节不等于选用其中全部机制。主观目标使用参考片段、评价问题或已标定指标，不写成没有依据的布尔值。

### AssetManifest：资源目录

包含稳定资源 ID、文件与内容哈希、资源类型、尺寸与坐标规范、实例化路径、碰撞、动画映射、能力标签和适用平台。

另记录风格标签、材质/动画版本与代表性检查结果，关联风格配置；目标尺寸和可射击部位是实际数据，不能只写“卡通、易瞄准”等推断。

建筑模块另外提供连接点；敌人提供可射击部位和可用动作；机关提供触发与结果接口。连接点等能力必须能在导入后的场景中定位。接口声明与测量/检查结果分开保存。

### LevelIR：关卡中间数据

包含版本、关卡 ID、生成种子、使用的能力/风格配置版本、人数配置、资源实例及变换、镜头路径与驻点、锚点与敌人路径、波次、攻击/任务的玩家范围、单人替代规则、推进条件、分支、双方重试边界和平台预算。稳定共享空间可以复用，人数不同的波次与任务配置分别验证。

每个对象有稳定 ID，关联需求与所选模板；设计意图等编辑元数据可以留在生成记录。事件通过对象 ID 和明确条件引用，不携带任意代码字符串。运行时可编译为 Godot Resource，以获得类型检查与引擎序列化。

### RunRecord：执行与证据记录

包含规格/设计依据/资源/风格配置/代码/IR/工具版本、参与人数、玩家输入源与能力参数、当前阶段、每项测试的要求 ID 与结果、平台画质与分辨率、日志和回放路径、修复次数及未验证项。

重启可以从已有产物继续；复用测试结果必须确认影响该测试的输入没有改变，不能把旧构建截图当新构建证据。结果状态在 [03 第 4 节](03-开发工作流与验收.md#4-验证与交付判定)统一定义。

## 5. 时间与判定的一致性

空间使用米，时间数据使用整数毫秒；画面坐标使用有效视口归一化坐标。相机 FOV 与显示画幅一起记录，不混用世界尺寸与屏幕占比。

第一版游戏逻辑使用统一的可暂停游戏时钟；输入和性能测量使用真实单调时钟。普通暂停停止战斗、装填、镜头和游戏计时。慢动作和“某计时不暂停”等规则只在需求要求时另行定义，避免提前维护多套演出时钟。

Godot 物理空间可能在输入回调时锁定，射线查询应安排到安全的物理回调。[官方射线说明](https://docs.godotengine.org/en/stable/tutorials/physics/ray-casting.html)

首版保存扳机按下时的瞄准位置，在安全查询时点使用**同一时点的相机和目标状态**计算命中，并记录延迟。不能混用旧相机与新目标状态，也不承诺所有机器都“零帧延迟”。判定与可见画面的偏差通过移动目标和移动镜头回放检查；只有测量证明需要时，再增加历史状态回溯。

## 6. 新机制的扩展方式

参数修改走数据；已有能力组合先验证相互作用；新增行为走代码扩展。所有能力明确输入事件、状态、输出结果、资源需求及测试。

以“击中手臂缴械，敌人随后逃离”为例：先定义持枪/缴械/逃离状态，约定奖励只能发生一次，再实现独立场景验证，最后让导演按该驻点任务决定缴械或逃离是否算完成。不是所有关卡都把缴械视为胜利。

通过独立行为测试与旧机制回归后登记能力版本，再用于关卡生成。AI 不能为通过测试把新要求替换为库内近似机制。

## 7. Review 重点

- 每个状态是否有明确拥有者，是否存在多个脚本同时修改弹药、血量或关卡进度？
- 规格、资源声明、实际运行结果是否区分，是否把推断当成已验证事实？
- 新机制能否局部加入并单独验证，是否会要求重新编写整个游戏？
- 时间、视口和对象 ID 是否一致，失败重试能否重建明确状态？
- 双方状态是否独立、共享结果是否唯一？输入适配证据与双人逻辑测试是否区分？风格变化是否能追踪到受影响的生成与测试？
