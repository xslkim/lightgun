# AI 开发光枪游戏：方法论与工作流

版本：0.4 · 2026-10-05。

## 1. 目标与范围

目标是：**用户准备好资源并描述机制后，AI 自动实现机制、生成场景和关卡、验证与修复，交付符合规格的 Godot 游戏。**

已确定使用 Godot，支持 PC 与 Android；第一阶段资源已准备，输入使用鼠标模拟；**双人游戏是标配**。起步方案采用 Windows PC、横屏、离线本地合作、共享画面、自动镜头推进与驻点交战，支持 1–2 人并以完整双人玩法为必需交付。共享画面等是实现默认值，双人是本项目要求，两者不混为可取消的默认配置。

首阶段实现双玩家输入与状态、共享战斗与合作规则、射击、敌人、镜头与波次、程序化场景、胜败重试、基础视听反馈、自动验证及双平台构建。装填是否启用及其方式由规格确定；人质、BOSS、分支、掩体、成长和排行榜按描述选用。实体光枪适配、模型生成、联网和商店发布另行规划。

自动测试用两路带玩家身份的虚拟指针模拟鼠标输入；人工试玩需两名玩家各有独立的瞄准与开火来源。具体设备方案需记录并在 PC/Android 分别验证，不能将共享一个系统光标或“鼠标＋机器人”当成真实双人输入验收。

## 2. 文档组织与阅读顺序

采用**统一入口，设计与工作流分层保存**。`design` 回答“游戏应具有什么规则与体验”；`ai-workflow` 回答“AI 如何实现、生成和证明它”。两层通过游戏规格连接，设计规则只定义一次。

当前共七篇文档，建议按下面顺序 review：

1. 本文：目标、边界、文档关系与旧文档取舍。
2. [核心玩法与战斗规则](design/01-核心玩法与战斗规则.md)：输入、武器、敌人、任务、难度、计分与双人合作。
3. [关卡节奏与内容结构](design/02-关卡节奏与内容结构.md)：驻点、镜头、波次、模板、分支与内容变化。
4. [视听反馈与交互规范](design/03-视听反馈与交互规范.md)：可读性、反馈、音频、双人 HUD，以及美术风格如何约束玩法。
5. [系统架构与数据契约](ai-workflow/01-系统架构与数据契约.md)：模块职责、四类数据、机制扩展。
6. [场景与关卡生成方法](ai-workflow/02-场景与关卡生成方法.md)：设计如何变成空间、取景、事件和可运行场景。
7. [开发工作流与验收](ai-workflow/03-开发工作流与验收.md)：六步生产、四层验证、修复及实施路线。

不把原 17 篇整体塞进 `ai-workflow`：那会把设计建议与工程步骤混在一起，也会重复定义镜头、敌人和验收。`design` 也不单独维护数据格式、任务清单或交付标准；这些以工程文档为准。示例代码集中在 `tools`，不扩充文档目录。

## 3. 方法与规则的使用方式

```text
用户描述＋资源
  → 依据 design 明确游戏规则、体验目标与默认值
  → GameSpec＋资源能力规划
  → 机制实现＋关卡中间数据 LevelIR
  → Godot 场景编译
  → 验证 → 定向修复
  → PC / Android 构建与证据交付
```

AI 负责理解、设计、写代码和定位问题；程序负责资源测量、几何检查、场景保存、运行测试和构建。开发时生成并保存关卡，运行游戏不依赖 AI 服务。已有能力复用参数与组合，新行为局部扩展代码。

设计文档使用稳定规则标识，例如 `DES-COMBAT-02`。标识用于追踪依据，不是已实现功能，也不强制开启所有机制。规则分为三种：

- **基线**：完整双人能力、规则语义明确、状态一致，危险有已声明且可执行的应对，结果和惩罚可理解。
- **默认建议**：未被描述覆盖时，AI 可采用并记录，例如驻点交战、按键装填。用户要求优先。
- **可选机制**：只在规格选用后定义参数、实现和验收，例如掩体、救援或动态难度。

GameSpec 保存需求 ID、相关设计规则、具体参数、例外和验收方式。数值由该游戏的规格与试玩标定；设计文档不声明普遍的反应时间、敌人数、关卡时长或通关率。几何、行为、视听和平台的验收职责见工作流，主观好玩程度需单独评价。

**美术风格是玩法生成的输入。** AI 需将实际资源的轮廓、部位尺寸、光照/背景、动画提示和特效成本转为风格配置及检查结果，用于取景、目标间距、应对窗口和平台预算。风格名称本身不能证明可读或性能合格；更换风格后按实际改变重验，不能直接沿用旧关卡通过结论。

## 4. 原 00–16 的审查与去向

原文件不再逐篇维护，内容已按职责重写合并：

- **00 总纲**：目标、边界与阅读地图归本文；“只有一个动词”“六条铁律”改为可检查的设计基线，删除品类历史与社区评价的推论。
- **01 历史全景、16 案例速查库**：删除独立篇章。仅保留靶场与定轨形态的选择方法；年代、销量、媒体评分、作品清单和市场成败不进入当前开发规范。以后需要对标研究时再作为独立研究任务核查。
- **02 世界观与题材**：合入关卡目标和视听一致性；删除“题材必须全盘绑定机制包”、市场情绪与传播承诺。
- **03 美术、09 特效、12 音频、13 UI**：合入视听规范；保留识别、状态反馈、混音、布局和菜单规则，补充美术风格对瞄准、节奏、合作与性能的影响。删除统一像素/角度/时长阈值、必做配音和名场面数量。
- **04 镜头、05 关卡**：合入关卡方法；保留导演、驻点、波次、模板和可感知分支，删除统一章节数量、固定战斗比例及“变体数量等于游玩小时数”的估算。
- **06 操作、07 敌人与 BOSS、08 道具武器、10 难度计分**：合入战斗规则；保留状态、应对、弹药、任务结果和调参方法。删除零帧保证、固定生理下限、全场景可破坏及一律禁随机等要求；成长和计分比较口径分别定义。
- **11 双人合作与社交**：按用户要求，双人作为本项目标配，合入玩法、关卡、视听、架构和验收；删除将双人当作所有光枪作品普遍义务的论证，保留本项目必需能力。排行榜、直播传播和远程串流仍不自动纳入范围。
- **14 输入抽象与跨硬件**：统一动作、坐标与判定一致性归架构；鼠标菜单归视听。型号、采购、多枪驱动、离屏检测和物理反馈另行适配，不要求首阶段兼容未知设备。
- **15 避坑清单**：有效检查归各篇 review 与工作流验收；删除重复清单，以及把评论或案例结论直接当发布门槛的内容。

旧文档从当前目录移除，历史版本仍可从 Git 查阅。不另留一套旧规范，避免 AI 同时读取互相冲突的要求。

## 5. 当前完成程度

当前交付的是待实施的方法论与工作流，以及一个数据预检演示；尚未实现玩法底座、场景编译器和自动试玩。文档里的模块、规则标识与生产阶段均不代表已存在工具。

样例位于 [tools/workflow-example](../tools/workflow-example/validate_workflow.py)，包含规格、资源元数据和三个驻点。它只检查部分引用、时间、终态和图结构；资源路径为示例，不证明真实场景或平台可用，也未完整实现本文的规则引用、双人状态、风格配置和数据契约。

在仓库根目录运行：

```powershell
python tools/workflow-example/validate_workflow.py
python tools/workflow-example/validate_workflow.py --self-test
```

自检包含一个正常样例和 12 类错误注入。演示时间值、单波限制和终态集合不是通用生成规则。报告通过 `--report <path>` 按需生成，不保留为常驻文档。完整交付判定见 [工作流第 4 节](ai-workflow/03-开发工作流与验收.md#4-验证与交付判定)。
